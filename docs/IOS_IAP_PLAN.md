# FleetFlow iOS app + Apple In-App Purchase — plan (step 1)

Status: branch `feat/ios-app` (from production commit 8aec5cab). Nothing published, no DB changes, no auth/CORS changes, no store accounts touched.

## 1. Build approach

### How FleetFlow builds today
`vite build` via `@lovable.dev/vite-tanstack-config` → TanStack Start (SSR) + nitro (Cloudflare target). The app depends on the server at runtime:
- `createServerFn` RPCs at relative `/_serverFn/<id>` (assistant, billing/plan change, Paddle portal, etc.), with the Supabase bearer attached by `auth-attacher`;
- server routes under `/api/public/*` (Paddle webhook, contact, expiry hooks);
- SSR `head()`/loaders and route-level auth redirects.

### Option A: static SPA bundle in the app, calling https://fleetflow.group
- Pros: the UI ships inside the binary (fast cold start, works offline for shell screens), so it reads most "native" for guideline 4.2.
- Cons:
  - TanStack Start has no supported SPA export in this Lovable config. We'd need a second build target and to rewrite every `/_serverFn` call to an absolute origin.
  - The WebView origin becomes `capacitor://localhost`, so we'd need CORS on fleetflow.group server functions and Supabase redirect-URL changes.
  - Server-fn ids are build-hash-bound: an app binary built from commit X breaks when the web is published at commit Y. That is a hard versioning problem with Lovable's frequent publishes.
  - Every UI fix needs an App Review cycle.

### Option B (chosen): `server.url = https://fleetflow.group` ("hosted shell") plus native plugins
- Pros:
  - Zero changes to the web build, auth, CORS or server functions. The WebView is same-origin with production.
  - Fixes ship instantly with each Lovable publish.
  - Capacitor still injects its bridge into the remote page (allowNavigation is limited to fleetflow.group), so native camera, push, status bar, splash and StoreKit work.
- Cons:
  - Needs connectivity. Mitigated by the bundled `ios-shell/offline.html` (`server.errorPath`).
  - **Guideline 4.2 (Minimum Functionality)** rejects apps that are "a repackaged website". We must ship real native value. This is the main review risk; see the checklist below.
  - Capacitor docs say `server.url` is "intended for live-reload". It is used in production by many apps, but App Review may probe it. A web publish can also change the app's behaviour without review, so we must not use that to swap reviewed functionality (guideline 2.5.2/3.3.2 spirit).

**Why B:** FleetFlow is server-coupled (SSR, server functions, Supabase sessions), and Lovable republishes often. Option A would break on every publish unless we froze server-fn ids. B gets a reviewable app without touching production. We can move to A later if 4.2 rejections persist.

## 2. In-app purchase design

### Rules that force IAP
- Under guideline 3.1.1, digital subscriptions bought *in the iOS app* must use IAP.
- FleetFlow is B2B SaaS, so 3.1.3(b) "multiplatform services" lets users access a subscription bought on the web. We just can't link to or advertise Paddle checkout inside the iOS app (unless we use the US-storefront link entitlement).
- Simplest compliant model:
  - In the iOS app, show IAP for companies with no active subscription.
  - Hide the Paddle checkout and portal links when `isNativeApp()`.
  - A company already on Paddle just signs in and works.

### RevenueCat (recommended) vs native StoreKit 2
- **RevenueCat:** receipt validation, App Store Server Notifications V2 ingestion, renewals, grace and billing retry, refunds, and a single webhook to us. Capacitor plugin: `@revenuecat/purchases-capacitor`. It is free up to $2.5k MTR, then 1%.
- **Native:** we'd need our own App Store Server API client (JWS verification, notifications V2, subscription status polling). That is more code and risk on top of the current webhook debt.
- **Recommendation:** RevenueCat.

### Product mapping (same plan keys as Paddle)
| Plan | Paddle price external_id | Paddle AUD/mo | Apple product id (proposed) | Apple tier |
|---|---|---|---|---|
| starter | starter_monthly | 49 | group.fleetflow.app.starter.monthly | nearest AUD tier ≈ 49.99 |
| growth | growth_monthly | 99 | group.fleetflow.app.growth.monthly | ≈ 99.99 |
| pro | pro_monthly | 199 | group.fleetflow.app.pro.monthly | ≈ 199.99 |
| business | business_monthly | 299 | group.fleetflow.app.business.monthly | ≈ 299.99 |

- All four go in one **subscription group** "FleetFlow Plans", ranked business > pro > growth > starter, so Apple handles upgrades and downgrades.
- The Paddle first-month AUD 9.99 discount maps to an **introductory offer** (pay-as-you-go, 1 month).
- Apple takes 15% (Small Business Program) or 30%. Decide whether to raise iOS prices.
- In RevenueCat, create one **entitlement per plan** (`starter`…`business`) and an offering "default" with the 4 packages.

### Identity
- RevenueCat `appUserID = company_id`, so the subscription belongs to the company, not the device. Call `Purchases.logIn(company_id)` after sign-in.
- Only users with **admin** role in the company can purchase. Enforce this in the UI, and in the webhook ignore (and flag) purchases whose app_user_id company has no admin attached.
- Never trust client-supplied company ids for role grants. This is audit must-fix 2 and must not be copied.

### Server sync: new route `src/routes/api/public/payments/revenuecat-webhook.ts` (to build in step 2)
1. Verify the `Authorization` header equals the secret `REVENUECAT_WEBHOOK_AUTH` (a constant-time compare). Reject with 401 otherwise.
2. Insert into `billing_events(id=event.id)`. On a conflict, return 200 (dedupe).
3. Ignore the event if `event.event_timestamp_ms` < `subscriptions.last_event_at` (ordering).
4. Map `INITIAL_PURCHASE`/`RENEWAL`/`PRODUCT_CHANGE`/`UNCANCELLATION` to status `active`, plan from `store_products`, and the period from `purchased_at_ms`/`expiration_at_ms`.
   - `CANCELLATION` sets `cancel_at_period_end=true` and keeps `current_period_end`.
   - `BILLING_ISSUE` sets `past_due`.
   - `EXPIRATION` sets `canceled` with period_end = expiration.
   - `REFUND`/`CANCELLATION` with reason CUSTOMER_SUPPORT sets `canceled` now.
   - `environment: SANDBOX` maps to `sandbox`, otherwise `live`.
5. Upsert `subscriptions` on `(provider='apple', store_original_transaction_id)` with `company_id = app_user_id` (validated to exist). **Never** touch `user_roles`.
6. If any DB error occurs, return 500 so RevenueCat retries.

### Unified entitlement
- `company_billing_state(company_id, env)` stays the single source of truth for web and app. It considers active rows from either provider (proposed migration step 4).
- The client keeps calling the same RPC. RevenueCat's client-side `customerInfo` is only used for instant UI after purchase, then the app refetches billing state.
- Conflict policy: if a company already has an active Paddle sub, the app hides IAP and says "Managed on the web". If an Apple sub is active, the web billing page shows "Managed in the App Store" and hides Paddle checkout and plan change.

### Proposed DB changes (NOT applied)
`docs/proposed-migrations/PROPOSED_0009_multi_store_subscriptions.sql` plus a rollback:
- `subscriptions.provider` plus Apple id columns, with nullable Paddle ids guarded by a CHECK;
- `last_event_id`/`last_event_at`;
- `billing_events` (idempotency, service_role only);
- `store_products` map;
- `company_billing_state` updated to be provider-agnostic.

Also needed later: `device_tokens` for push.

## 3. Blockers from BILLING_AUDIT_t57 (fix before any IAP goes live)
1. **Must-fix 1:** the webhook ignores Supabase errors and returns 200. The same pattern in the Apple webhook would silently lose purchases.
2. **Must-fix 2 (high):** admin is granted from client customData. Fix this before adding a second purchase path, and do not mirror it.
3. **Must-fix 4:** dedupe and ordering. The `billing_events`/`last_event_at` design above assumes it is shared with Paddle.
4. **Must-fix 5:** the cancel period_end gap. Grace semantics must match across providers.
5. **Must-fix 7:** the paywall is client-only. With an app that hides the paywall when `isNativeApp()`, server-side enforcement matters more.
6. **Must-fix 8:** fix the MRR map, and add the Apple rows (net of Apple's cut) to platform stats.

## 5. Auth/CORS changes required (NOT made)
- **With the chosen approach (server.url = fleetflow.group): none for core sign-in.** The WebView origin is https://fleetflow.group.
- Watch-outs:
  - **Google/OAuth sign-in in WKWebView** is blocked by Google ("disallowed_useragent"). If Lovable cloud-auth offers Google, it must open in `ASWebAuthenticationSession`/Browser plugin with a custom-scheme or universal-link redirect. That would need a Supabase redirect URL added (e.g. `group.fleetflow.app://auth-callback`). If any third-party login is offered, **Sign in with Apple** is required (guideline 4.8).
  - Email links (reset password, invites) open Safari, not the app, unless we add **Universal Links**: an `apple-app-site-association` file on fleetflow.group plus the Associated Domains capability. That is a web publish, so it needs separate approval.
  - Account deletion must be available in-app (guideline 5.1.1(v)). Check that one exists before submission.
- Option A, if ever adopted, would need CORS for `capacitor://localhost` on server functions and Supabase redirect URLs. Not recommended.
